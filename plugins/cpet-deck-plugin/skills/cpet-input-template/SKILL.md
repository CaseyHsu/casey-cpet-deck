# CPET Input Template（v1.5 — 簡報內容轉譯技能）

把「素材檔案」或「一句需求」轉譯成一份**你會親自看過、確認版面決策的中介文件**
（`input_template.md`），而不是讓 `cpet-yslai-pptx` 在建置 plan.json 的當下，即時、隱性地
幫你做完所有版面與素材判斷。核心價值不在「能寫出符合語法的文件」，而在**把原本鎖死在最終
產物裡、事後難以追溯的判斷過程，提前變成一個可以審查、可以整份重跑的檢查點**。

## 與鄰近技能的分工

| 技能 | 職責 |
|---|---|
| **`cpet-input-template`（本技能）** | 素材/需求 →（編排呼叫 doc-coauthoring）→ **轉譯**成 `input_template.md` ＋ 素材處理清單 |
| `doc-coauthoring` | 通用內容共創（脈絡收集、逐段精修、讀者測試），本技能內部第一步呼叫它 |
| `cpet-infographic-forge` | **從資料生成**向量圖（流程圖、矩陣、時程） |
| `cpet-figure-prep` | **整理既有點陣圖**（去背、裁邊、轉檔、截圖標註） |
| `cpet-yslai-pptx` | 把 `input_template.md` **組裝**進投影片，產出 `.pptx` + `plan.json` |

本技能只做轉譯，**不呼叫 `build_deck.py`、不碰 `figs/`、不呼叫 forge 或 figure-prep，
不產出 `.pptx` 或 `.json`**。轉譯完成就停下來，下游三個技能一律由使用者手動觸發。
唯一例外是第 9 步的數據查核：它只讀簡報與講稿、不修改任何檔案，可以在任何階段執行。

## 為什麼需要這個技能

| 若跳過本技能，直接把素材丟給 cpet-yslai-pptx | 後果 |
|---|---|
| 「文稿→投影片類型」的映射在生成 `plan.json` 當下即時、隱性完成 | 沒有中介產物可以在建置前審查版面決策，只能等看到 pptx 成品才發現「這頁我想要 table 不是 bullets」 |
| 事後修訂只能直接改 `plan.json` | `plan.json` 是建置產物，不是設計來人工編輯的；改到一定輪次後就與任何可讀來源脫鉤，之後要靠考古反推才能重建對應的來源文件 |
| doc-coauthoring 的內容共創與版面轉譯揉在同一步 | 兩件性質不同的判斷（「內容想清楚了嗎」與「這段適合什麼版面」）沒有分開，出錯時不容易定位是共創階段還是轉譯階段的問題 |
| 素材裡的圖片一律當「使用者已備妥可直接用」處理 | 螢幕截圖沒去背、EMF 沒轉檔、解析度不足沒被抓到，這些屬於 `cpet-figure-prep` 的職責，跳過本技能就不會被路由過去 |

`input_template.md` ＋ 素材處理清單.md 是本技能產出後，你唯一需要看過確認的東西；確認後
才手動觸發 `cpet-yslai-pptx`（與需要的 `cpet-infographic-forge` / `cpet-figure-prep`）。

## 環境準備

**依賴 `doc-coauthoring` 技能**，執行前確認它已安裝——本技能第一步就是編排呼叫它，不是
重寫一份內容共創方法論。

**「單一事實來源」原則，依實際探測結果分兩種正常模式（v1.3 起）**：
本技能**不內建 DSL 語法的靜態複本**——
`cpet-yslai-pptx/assets/input-templates/input_template.md` 與該技能 `SKILL.md` 步驟 0／0.5／1 才是語法與
規則的權威定義，會隨版本更新。故執行本技能的第一件事是**實際去找找看
環境中有沒有裝 `cpet-yslai-pptx`**，依找不找得到分兩種**皆屬正常**的情況。
**判定依據只有「找不找得到」這件事**，不要以執行環境的名稱（Claude Code／
Chat／Cowork）預設結果——任何環境都可能裝或沒裝（例如 Cowork 現在可以把
Git repo 加成 marketplace 來安裝 plugin），也不要把第二種誤判為異常：

1. **能在環境中定位到已安裝的 `cpet-yslai-pptx` 技能目錄**（搜尋
   `cpet-yslai-pptx/assets/input-templates/input_template.md` 這個相對路徑落在哪個安裝路徑
   下，不同環境的絕對路徑前綴不同，不要假設固定路徑）→ 讀取它當下的語法表與規則，
   忽略 `references/translation-rules.md` 的內容，這是**動態模式**，語法保證即時。
2. **在環境中找不到已安裝的 `cpet-yslai-pptx`** → 改依
   `references/translation-rules.md` 的規則快照運作，
   這是**快照模式**，**不是錯誤、不需要在決策摘要中當成異常提醒使用者**——只需在
   決策摘要末尾照常標註「本次轉譯依快照模式（`references/translation-rules.md`，見其
   檔頭標示的對應版本）運作」一句話讓使用者知情即可，不需要額外警告語氣。快照的內容
   準確度由 `cpet-yslai-pptx/MAINTENANCE.md` 打包檢查清單的同步紀律把關（該技能每次
   DSL 語法變更時人工同步），本技能執行時不需要、也無法自行驗證快照是否為最新版。

兩種模式**只有第 3 步「讀取權威語法」的來源不同，其餘工作流程步驟完全一致**。

## 工作流程

### 1. 判斷起點，鎖定簡報資訊（情境四問）

若使用者提供了素材檔案（Word／會議紀錄／舊簡報／草稿／論文段落／既有截圖照片），內容
共創階段以「讀素材」為主；若只有一句需求或主題，內容共創階段從零開始。不論哪種起點，
開始轉譯前都要先確認四件事（若使用者需求裡已講明就不重問，一次問完不分批）：

1. 簡報類型（研究成果／期末報告｜講義／weekly｜短篇數據／SOP）→ 決定敘事骨架
2. 是否有配套書面報告 → 有→圖表用章節式編號；沒有→流水號
3. 是否為教學情境 → 是→結尾加 Homework 頁
4. 語言與對外程度 → 決定中英文分工或全英文

同時確認標題（英/中）、報告人、指導教授、日期等封面資訊。

### 2. 編排呼叫 doc-coauthoring，完成內容共創

觸發 `doc-coauthoring` 技能執行脈絡收集→逐段共創→讀者測試，**明確告知它以下引導目標**
（不是讓它全然通用地運作，而是用這些目標收斂）：

- 步驟1已確認的簡報資訊（類型、語言、教學情境等）
- 裁剪紀律：內容最終要落在「一頁一訊息、單頁 bullet ≤6 條、單頁區塊數 ≤3」的密度，
  共創階段就以此為目標收斂，不要先寫成長文再回頭砍

產出一份組織良好、章節分明的**散文草稿**——這階段不需要、也不應該出現 `[layout:]`、
`[figure:]` 等 DSL 標記，那是下一步的職責。若使用者在共創過程中口語提到明確的版面偏好
（例如「這段我要左文右圖」），記下來供下一步轉譯時採用為強提示。

### 3. 讀取 cpet-yslai-pptx 當下權威語法（動態模式）或規則快照（快照模式）

依「環境準備」一節判斷所在環境屬於哪一種模式：**動態模式**下定位並讀取已安裝的
`cpet-yslai-pptx` 的 `input_template.md` 與 `SKILL.md` 語法表；**快照模式**下直接
採用 `references/translation-rules.md`。兩種模式皆屬正常運作，不需要在決策摘要中
以警告語氣呈現，僅需照常標註本次採用哪一種模式。**動態模式下**若讀到的版本與
`references/translation-rules.md` 記載的不一致，仍在決策摘要中註明（代表快照需要
有人回頭同步，這是判斷「快照是否過期」的少數機會之一，值得記錄）。

### 4. 逐段轉譯：決定每頁的區塊組成

`cpet-yslai-pptx` v2.8 起，排版式樣由「文字／圖／字卡／表格」四種區塊**依文稿出現順序
垂直堆疊**決定，不設式樣編號讓你宣告。轉譯時的工作是「決定這頁該有哪些區塊、依什麼順序
寫」，不是「幫這頁選一個式樣編號」——寫什麼就排什麼。唯一需要明確指定的是左文右圖
（`[layout: two_col]`），因為左右分欄與垂直堆疊是正交的兩種切法。

一頁最多三個區塊，超過就拆頁；含圖的頁面，圖片預期取得至少一半的內容區高度。完整的
「內容性質→區塊/語法」對照表、字卡群語法、語意項目符號使用邊界、量化上限，見
`references/translation-rules.md`——**先讀那份文件的判斷邏輯，但語法本身以第3步驟讀到的
即時版本為準**。

### 5. 路由視覺元素：新畫圖走 forge，既有圖走 figure-prep

轉譯過程中，若某段內容需要視覺元素但手邊還沒有可直接用的圖檔，先判斷：

- **概念尚不存在，要無中生有畫一張圖**（抽象概念/流程/關係圖）→ 佔位鍵
  `PENDING:forge-鍵值`，供 `cpet-infographic-forge` 使用
- **已有實體點陣圖，只是不能直接放**（白底有框、螢幕截圖需標重點、EMF/WMF 向量圖、
  解析度存疑）→ 佔位鍵 `PENDING:figprep-鍵值`，供 `cpet-figure-prep` 使用

**教學／SOP 類簡報的操作截圖一律走 figprep**。判斷細節與兩種佔位鍵各自要記錄的內容規格，
見 `references/translation-rules.md` 與 `references/output-templates.md`。

### 6. 輸出三份文件，附上決策摘要，停下來

依 `references/output-templates.md` 的格式輸出 `input_template.md` ＋ 素材處理清單.md ＋ 數據查核表.md。

**數據查核表**的骨架用 `scripts/claim_check.py suggest input_template.md` 產生（列出每個「數字＋單位」與出現頁），
再逐列補上：
- `anchor`：讓這個數字有意義的條件（例如 `9 000 rpm`、`rated torque`），同一個量在不同頁要用同一個 anchor。
- `kind`：命令值／實測值／模擬值／計算值／文獻值。同一個 anchor＋單位若有兩種以上性質，
  簡報上每次出現都必須標明（`labels` 填會出現在數字前面的標籤字，中英文都可，例如 `measured;實測`）。
- `source`：來源檔與欄位或頁碼。**素材裡找不到來源就填「待填」，不要推測**——在決策摘要列出待填清單請使用者補。
- 同一個數字若是由別的數字算出來（誤差、比例、加總），另開一列並在 `source` 寫算式。
**輸出後主動列出決策摘要**（哪些頁用了什麼版面組成、為什麼；哪些視覺元素路由到 forge、
哪些路由到 figprep、為什麼）——不要只是把檔案丟出來要使用者自己讀 DSL 標記反推邏輯，
決策本身才是使用者要審查的東西，檔案只是決策的存檔格式。

列完摘要後**停下來**。不自動觸發 `cpet-yslai-pptx`、`cpet-infographic-forge` 或
`cpet-figure-prep`，這三步都需要使用者確認後手動觸發。

### 7. 修訂模式（已存在 input_template.md 時）

執行前先檢查工作資料夾是否已有 `input_template.md`。若有，代表這是修訂而非初次生成：

- 讀取舊版 `input_template.md` 與素材處理清單.md，加上使用者這次提出的修改意見
- **不重新呼叫 doc-coauthoring 從零共創**，把修改意見直接套用在既有草稿基礎上
- **整份重新輸出**兩份文件，不做局部 patch——版面與素材判斷涉及跨頁一致性（章節編號、
  Part 清單同步、running title 一致性、圖表間視覺語言一致），局部編輯容易破壞這些全局
  狀態
- 決策摘要**只列這次改動了哪裡、為什麼**，其餘頁面註記「維持原判斷」，不要重複列出全部
  頁面的理由讓使用者每次都要重新篩一遍差異

修訂鐵律：使用者事後對 `.pptx` 成品不滿意，一律回到本技能整份重跑，**不要直接改
`plan.json`**——那是建置產物，不是可編輯的來源。

### 8. `PENDING:` 佔位鍵回填（v1.2 新增，機械式操作，非轉譯判斷的一部分）

`cpet-infographic-forge` 或 `cpet-figure-prep` 完成處理後，用
`scripts/backfill_pending.py` 把兩者的 `manifest.json` 讀出的產出路徑，回填進
`input_template.md` 對應的 `PENDING:forge-鍵值`／`PENDING:figprep-鍵值`：

```bash
python scripts/backfill_pending.py input_template.md \
    --forge-manifest <forge輸出目錄>/manifest.json \
    --figprep-manifest <figprep輸出目錄>/manifest.json
```

`cpet-figure-prep` 側需先用其 `manifest` 子命令登記鍵值對應（**在該技能的預覽拼接圖
人工確認閘門之後才登記**，見 `cpet-figure-prep` SKILL.md）：

```bash
python figprep_scripts/figprep.py manifest --from 鍵值對應.txt -o figprep_manifest.json
```

**這一步是機械式字串取代，不是轉譯判斷**——判斷「這頁該用哪個佔位鍵、鍵值該叫什麼
名字」仍是本技能第5步的職責。回填腳本只做三件事：讀 manifest、找 `PENDING:` 字串、
換成相對路徑（依 v4 指引「跨 session 重建應使用相對路徑」的既定規則）。原檔案回填前
自動備份為 `.bak`；manifest 未涵蓋或標記失敗的鍵值維持原樣不動並在執行結果中列出，
不會讓使用者誤以為已經全部處理完成。

回填後**仍須人工確認回填結果**（圖片路徑是否正確、多個鍵值有沒有對錯位置）再手動觸發
`cpet-yslai-pptx` 建置——回填自動化省的是「手動打字複製路徑」這個機械動作，不是省略
確認這一步。

### 9. 數據查核（v1.5 新增，唯讀，可在任何階段執行）

簡報建好之後、每次改了數字或講稿之後，用數據查核表檢查簡報、備忘錄與講稿：

```bash
python <skill_path>/scripts/claim_check.py check 數據查核表.md deck.pptx [talk.json] [其他 .md/.txt]
```

- `MISMATCH`：某處的數字不在查核表裡（打錯、用了舊數字，或是查核表漏了一列）→ 回 1。
- `UNLABELED`：同一條件下有命令值與實測值兩種數字，這一處卻沒標明是哪一種 → 警告（`--strict` 時回 1）。
  兩頁的數字看起來互相矛盾，多半就是這一種。
- 查核只比對數字，不判斷主張本身是否站得住（例如差異是否在量測誤差內）；那仍需人工看數據。

## 交付前的自我檢查

- [ ] 情境四問（簡報類型/書面配套/教學情境/語言）已確認，沒有用猜測值
- [ ] 已依環境判斷模式（動態讀取已安裝 `cpet-yslai-pptx` 語法，或 Chat/Cowork 快照
      模式依 `references/translation-rules.md`），兩者皆屬正常，決策摘要已標註採用
      哪一種、動態模式下若發現版本落差已記錄
- [ ] 每頁區塊數 ≤3、單頁 bullet ≤6 條、Outline ≤8 項，沒有留到建置階段才被 `plan_lint`
      擋下
- [ ] 每張需要視覺元素的頁面，都已判斷路由到 forge 還是 figprep，佔位鍵前綴正確
- [ ] 圖片路徑（含未來要回填的路徑）用相對路徑，不是本次 session 的絕對路徑
- [ ] 決策摘要已列出，且是修訂模式時只列本次改動、不是全部重列
- [ ] 數據查核表每個數字都有 anchor 與 kind；找不到來源的列標「待填」並列在決策摘要，沒有推測來源
- [ ] 沒有自動觸發下游任何技能，停在三份文件交付使用者確認這一步
- [ ] 若執行了 `PENDING:` 回填，回填結果已人工確認過路徑正確，不是只看腳本沒報錯就當完成
