## §1 簡報資訊四問

| 問題 | 選項 | 影響 |
|---|---|---|
| 簡報類型 | 研究成果／期末報告 ｜ 講義/weekly ｜ 短篇數據/SOP | 決定敘事骨架分流 |
| 書面報告配套 | 是／否 | 是→圖表章節式編號「圖 2.7」；否→流水號「圖 1」 |
| 教學情境 | 是／否 | 是→結尾加 Homework 頁 |
| 語言 | zh-TW／en | 對外口試會議→en |
| 標題樣式（v2.2） | 三層／雙層 | 雙層＝章名與頁名同一行；研討會官方模板建議雙層 |
| 模板（v2.2） | 實驗室／大會官方模板 | 官方模板需要描述檔（`cpet-yslai-pptx/assets/profiles/`），研討會口頭報告每卡 ≤3 點 |

不論簡報類型為何，**結尾一律自動加致謝頁**（這點不因「成果報告型」而例外——早期版本
曾有「成果報告型不加 Thanks 頁」的規則，已於 v2.6 移除，轉譯時不要沿用這個過時說法）。
可用 `[closing: 自訂感謝詞]` 改結尾文字。

## §2 標題階層（三層）

| 文稿寫法 | 產出 | 字級／樣式 |
|---|---|---|
| `## 一級標題` | 章 running title | 40pt 藍、置中 |
| `### 三級標題` | 頁大標 | 32pt bold navy、靠左、前置箭號 |
| `[sub: 一句話]` | 頁副標（選填） | 16pt 灰 `#6B7280` |

同章連續多頁只需第一頁寫章名，後續自動沿用。

## §3 排版式樣：由區塊順序決定，不宣告編號

一頁由「文字／圖／字卡／表格」四種區塊，依文稿中出現的順序垂直堆疊，五種排版式樣全是
排列組合：

| 式樣 | 文稿怎麼寫 |
|---|---|
| 上文＋下圖 | 段落文字，接一個 `[figure:]` |
| 左文＋右圖 | `[layout: two_col]`（唯一需要明確指定的，左右分欄與垂直堆疊正交） |
| 左文＋右公式 | 同樣 `[layout: two_col]`，右欄改用 `[eq-right: LaTeX]`（見下方說明） |
| 上文＋左右兩圖 | 段落文字，接兩個 `[figure:]` |
| 上文＋圖＋字卡 | 段落文字，接一個 `[figure:]`，接 `[card:]` |
| 上文＋兩圖＋兩字卡 | 段落文字，接兩個 `[figure:]`，接兩個 `[card:]` |

**不要在轉譯輸出裡設「式樣編號」欄位**——那是把工具的內部結構外露給使用者，寫什麼就排
什麼，`[layout:]` 只在要覆寫預設判斷時才用，不是每頁必填。

**`two_col` 右欄是圖還是公式，由內容本身決定**：右欄放使用者提供或待路由的圖片時用一般
`[figure:]`；右欄是要驗證的關係式（而非流程圖/波形圖）時改用 `[eq-right: LaTeX]`，並比照
一般公式規則附 `[note: 物理意義]`——這是 Casey「文字先建立直覺、公式後驗證」偏好在左文右
式版面的具體寫法，不要把該放公式的位置誤路由成 forge 示意圖。`[eq-right:]` 對應
`plan.json` 的 `two_col.right.latex`／`right.note` 欄位，不在 SKILL.md 正式語法表列舉的
獨立 DSL 標籤之列，屬於範本內建的填寫慣例，轉譯時仍應遵守。

## §4 完整語法表（快照，實際以即時讀取版本為準）

| 語法 | 意義 | 對應 plan 欄位 |
|---|---|---|
| `## 一級標題` | 一章 → running title | `section` |
| `### 三級標題` | 章內一頁 → 頁大標 | `title` |
| `[sub: …]` | 頁副標 | `subtitle` |
| `[layout: 類型]` | 覆寫版面判斷（bullets／equation／figure／two_col／table／closing） | `type` |
| `[section: Part-I: … \| Part-II: …]` | 多 Part 方法章，每 Part 開頭自動放進度回訪頁 | `section` 頁 |
| `[intro: …]`／`[note: …]`／`[assumption: …]` | 公式的開場句／物理意義／假設 | `equation.blocks[]` |
| `[eq-right: LaTeX]`（配 `[note: …]`） | `two_col` 右欄放公式而非圖片時使用 | `two_col.right.latex`／`.note` |
| `[figure: 路徑 \| caption \| source: … \| takeaway: …]` | 圖＋說明＋出處＋量化結論 | `images[]` |
| `[source: …]` | 同區塊多圖共用出處（單獨一行） | `source_shared` |
| `[cards: 欄數]` | 宣告接下來的字卡排成幾欄（1–4） | `bands[].cols` |
| `[card: 標題 \| 內文]` | 一般字卡（淺灰底） | `cards[]` |
| `[card-accent: 標題 \| 內文]` | 強調字卡（淡橙底，一頁最多一張） | `cards[].accent` |
| `[card-num: 編號 \| 標題 \| 內文]` | 數字圓徽章字卡（順序帶訊息時才用） | `cards[].badge` |
| `[kpi: 數值 \| 標籤 \| 說明]` | 大數值卡 | `cards[].kpi` |
| 條列行首 `(+)`／`(-)`／`(>)` | 語意符號：勾／叉／箭號 | `bullets[].mark` |
| `[highlight: 關鍵字]` | 表格中該列整列橙底強調 | `highlight_rows` |
| `[takeaway: …]` | 該頁一句話結論（navy 實心橫幅＋白字，**不是綠色**） | `takeaway` |
| `[remarks]…[/remarks]` | 收錄至簡報末 Remarks 章節 | Remarks 章 |
| `[closing: 自訂感謝詞]` | 自訂結尾頁文字 | `closing` |
| `!!片語!!` | 行內重點（紅粗體；takeaway 內為黃字放大）。每卡 1–2 個、每條結論 ≤3 個 | 任何文字欄位 |
| `[card-tint: 色 \| 標題 \| 內文]` | 淡底字卡：blue／orange／vermilion／green（green 需雙重編碼） | `cards[].tint` |
| `[chevron: 標題 \| 說明]`／`[chevron-accent: …]` | 流程階段箭頭，連續 3–5 行成一組 | `chevrons` band |
| `[lane: 標籤 \| 色]`＋`[lane-item: 圖或文字 \| 圖說]`＋`[lane-kpi: 數值 \| 說明]` | 並列對照泳道（傳統 vs 本文），2–3 條 | `lanes` band |
| `[notes: …]` | 該頁備忘錄 | `notes` |
| `### [backup] 頁名` | 備用頁（放到致謝頁之後） | `backup: true` |

**何時用 chevrons／lanes**（轉譯判斷）：方法章的「框架總覽」頁、步驟有先後且 3–5 步 → chevrons；
「傳統做法 vs 本文做法」同一流程的並列對照、且兩邊各有 2–4 個對應步驟與一個成果數字 → lanes。
lanes 內的圖片照一般圖片路由（§10）。只有兩三點差異的比較，用兩張 `[card-tint:]` 就夠，不要硬做泳道。

## §5 字卡群用法

字卡內文可寫段落，或用「- 」條列（條列支援 `(+)`／`(-)`／`(>)` 前綴）：

```
[cards: 2]
[card: 文獻 [11]　同規格馬達之兩級式平台 |
  - 四開關升降壓 DC/DC + VSI
  - (+) 低速輕載效率提升最高 23.55%]
[card: 兩級式架構之本質限制 |
  - (-) 兩次能量轉換損耗
  - (-) 控制迴路相互耦合]

[card-accent: 對策 | 單級 Y-VSI：一級內同時升降壓，內建 LC 濾波直接輸出正弦]
```

字卡預設用箭號項目符號，與目錄／Outline 一致；要數字徽章才用 `[card-num:]`，保留給
「順序本身帶訊息」的有序步驟，不要用在一般並列項目上。

## §6 語意項目符號使用邊界

| 前綴 | 字形 | 顏色 | 只用於 |
|---|---|---|---|
| `(+)` | 勾 | Blue `#0072B2` | 研究貢獻、實驗結果驗證 |
| `(-)` | 叉 | Vermilion `#D55E00` | 前人方法缺陷、研究動機痛點 |
| `(>)` | 箭號 | navy `#14274E` | 演算法執行順序、實驗步驟 |
| 無前綴 | 一般箭頭 | 藍 | 一般內文 |

這三個只用於上述語境，不得當一般裝飾——濫用會讓讀者不再相信符號帶有訊息。轉譯時若某段
內容不屬於「貢獻/缺陷/步驟」三類，一律用無前綴的一般條列。

若轉譯輸出的文件本身要描述這些符號給人看，用文字描述（「勾號」「叉號」），不要直接貼
emoji 字元——PowerPoint 端刻意避開帶 emoji 呈現變體的碼點，貼 emoji 字元容易造成誤解。

## §7 圖片來源標註

```
[figure: figs/topo.png | 圖 1.2 三種升降壓拓樸 | source: [10] X. Liu et al., IEEE TPEL, 2023.]
```

**取自網路、文獻或他人簡報的圖必須標 `source`**（網址或 IEEE 引用格式）——學術誠信要求，
非排版偏好。自繪圖與本文實測圖不受此限，但建議標「本文實測」以與外部素材區別。轉譯時
凡是素材來源判斷為「非使用者自製、非本次實驗產出」的圖片，一律要求填 `source`。

同一區塊多圖共用出處時，用單獨一行 `[source: …]`。

## §8 表格整列強調

```
[highlight: 本文]
```

把含該關鍵字的資料列整列套淡橙底＋粗體，用於「本文」列或最佳結果列。表格下方可直接接
`[card-accent:]`，構成「表格＋結論卡」的式樣。

**表格其他覆寫選項**（建構器有預設行為，通常不需要轉譯時手動指定，僅在預設不合適時使用）：

- 第一欄預設視為「項目欄」（淡藍底＋粗體）——若第一欄不是項目名稱而是一般數據欄（例如
  全部欄位都是同質數值），轉譯輸出可加註 `[first_col_item: false]` 關閉這個樣式，對應
  `plan.json` 的 `"first_col_item": false`。這是 input_template.md 有明確文件化的標籤。
- 欄位對齊（整欄短內容置中、含長句靠左，建構器自動判斷）可用 `plan.json` 的
  `"col_align": [...]` 逐欄覆寫，但**目前 input_template.md 沒有對應的方括號標籤**——
  若轉譯階段判斷某張表格的自動對齊會不理想，在決策摘要裡用文字說明「建議欄位對齊」，
  交由後續撰寫 `plan.json` 的步驟手動加這個欄位，不要自行發明一個
  `[col_align: ...]` 語法寫進 input_template.md（那不是即時語法真的支援的標籤，寫了
  下游也不會認得）。

## §9 量化上限（避免建置階段被 `plan_lint` 擋下）

| 項目 | 上限 | 級別 |
|---|---|---|
| 一頁的區塊數（文字／圖／字卡／表格） | ≤3 | **錯誤**（會中止建置） |
| 單頁 bullet 條數 | ≤6 | 警告 |
| Outline 項數 | ≤8 | 警告 |
| 頁大標顯示寬度（全形字計 1、半形計 0.5） | ≤20 | 警告 |
| 一頁的 accent 強調字卡 | ≤1 張 | 警告 |
| 公式 | 每條必附 `[note:]` 物理意義 | 警告 |
| 外部圖片 | 必附 `source` | 警告 |
| 圖檔路徑不存在 | 直接中止建置 | **錯誤** |
| `!!` 沒有成對 | — | **錯誤** |
| 研討會口頭報告每張字卡條列 | ≤3 點 | 警告 |
| 全簡報語意色（含結論橙，淡底卡與泳道都算） | ≤3 種 | 警告 |

轉譯時應在這些上限內完成拆頁與裁剪，不要指望留到建置階段才被攔截修正——那樣使用者要
多一輪來回。

**路徑格式**：`input_template.md` 裡引用的圖片路徑一律用**相對路徑**（相對於
`plan.json` 所在目錄）。Cowork 沙箱的絕對路徑含 session 專屬字串，換一個新 session 就
失效；若這份文件預期跨 session 保存重建，相對路徑是必要習慣，不要依賴 lint 工具兜底。

## §10 視覺元素路由判斷（forge vs figprep）

| 情況 | 判斷依據 | 路由 | 佔位鍵前綴 |
|---|---|---|---|
| 概念尚不存在，需要「無中生有畫一張圖」 | 素材裡沒有對應的實體檔案，是抽象概念/流程/關係要視覺化 | `cpet-infographic-forge` | `PENDING:forge-鍵值` |
| 已有實體點陣圖，但不能直接放 | 白底有框／螢幕截圖需標重點／EMF/WMF 向量圖／解析度存疑 | `cpet-figure-prep` | `PENDING:figprep-鍵值` |

**教學／SOP 類簡報的操作截圖一律走 figprep**，不要誤判成「無中生有畫一張示意圖」而路由
到 forge——那樣會畫出一張跟實際畫面對不上的示意圖，失去截圖佐證的意義。

figprep 條目不要預先猜測紅框像素座標——`cpet-figure-prep` 自己有 `locate` 子命令（OCR
或 region+snap 兩條路徑）取代肉眼估座標，轉譯階段只需要用文字描述「要框住哪個元素」，
把定位工作留給下游技能。

## §11 素材處理清單的配色與品質規範（forge 條目專用）

forge 條目除了描述內容規格外，應附上以下配色與品質提醒，供 `cpet-infographic-forge`
產圖時遵守（詳細硬規則見 `cpet-yslai-pptx` 的 `references/lab-style-conventions.md`
§2.5–§2.7，此處僅摘要供轉譯時快速核對）：

**結構色**（不計入色數限制）：navy `#14274E`（標題/表頭）、`#1F2937`（正文）、
`#6B7280`（副標/註腳）、`#F5F7FA`／`#D6DEE9`（卡片底/框線）。

**語意色**（一律取自 Okabe-Ito 色盲友善色票）：Orange `#E69F00`（結論/主強調）、
Blue `#0072B2`（對照/次強調）、Vermilion `#D55E00`（警示/差異）、Bluish Green
`#009E73`（第四類別，僅圖表內部可用，版面層不用）。

**六條硬規則**：(1) 禁止純紅＋純綠語意對立，改用 Orange vs Blue；(2) 語意色單頁 1
種為原則、最多 2 種，全簡報 ≤3 種（圖表內部類別色不受此限）；(3) 顏色不得為唯一辨識
依據，須併用形狀/線型/文字標籤；(4) 黃 `#F0E442` 只作填色，細線與文字禁用；(5) 連續量
/熱圖用 viridis/cividis，不用 Okabe-Ito；(6) 交付前做灰階測試，去飽和後仍須靠明度可分。
補充：橙不當文字色，橙底文字一律用 navy 或深橙 `#8A5A00`。

**版面地位**：一頁若含圖表，圖表區應取得內容區至少一半高度，forge 條目應據此建議適當
長寬比，過於狹長的圖會浪費橫向空間。

**解析度**：以常見 6 吋置入寬度計，原圖至少 660px 寬、建議 900px 以上（投影 ≥110dpi、
列印 ≥150dpi）。forge 與 figprep 條目都應把預計置入寬度寫進去，供下游技能直接使用。
